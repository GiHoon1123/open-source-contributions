## 2. 배경 지식

### 2.1 HTTP 상태 코드, 그리고 "실제 응답"과 "문서"의 구분

서버는 요청마다 세 자리 성적표를 하나 붙여 답한다: `200 성공` / `201 생성됨` / `400 요청이 이상함` / `404 없음` / `500 서버 폭발`. 규칙은 단순하다 — **399 이하 = 성공 계열, 400 이상 = 에러 계열.**

이번 이슈에서 말하는 "200"은 **실제 응답이 아니라 API 설명서(Swagger 문서)의 항목**이다. Swagger 문서는 메뉴판과 같다 — "이 API는 성공하면 200으로 이런 데이터를, 실패하면 400으로 이런 에러를 준다"는 **가능한 결과의 목록**. 한 요청에 코드는 하나만 가지만, 메뉴판에는 모든 가능성이 다 적혀 있어야 한다. 버그는 서버 동작이 아니라 **메뉴판에서 200 항목이 증발**하는 문제였다.

하나의 엔드포인트는 호출할 때마다 다른 응답을 낼 수 있다 — 어떤 요청은 정상 처리돼서 `200`이 나가고, 어떤 요청은 검증 실패 등으로 `400`이 나갈 수 있다. 그래서 `@ApiResponse` 데코레이터가 **추가로** 붙었을 때, 그 상태값이 무엇이냐에 따라 자동 추론과의 관계가 달라진다:

- **에러 상태(4xx/5xx)를 명시** — "이 엔드포인트가 실패할 수도 있다"는 걸 추가로 문서화한 것뿐. 원래 있어야 할 자동 추론 `200`과 **충돌 없이 공존**해야 한다.
- **성공/리다이렉트 상태를 명시** (예: `HttpStatus.CREATED`) — "나는 200이 아니라 201로 응답한다"고 **성공 응답 자체를 재정의**한 것. 이 경우 자동 추론된 기본 `200`을 그대로 두면 중복이므로 **생략**하는 게 맞다.

### 2.2 Swagger CLI 플러그인 — 컴파일 시점에 문서를 채워주는 도구

응답 문서를 전부 손으로 적는 건 고역이라, `@nestjs/swagger`에는 CLI 플러그인이 있다. **코드가 실행되기 전, 컴파일 단계에서** 소스를 분석해 문서용 데코레이터를 자동으로 심는다:

```ts
@Get()
getExample(): ExampleDto { ... }
// 플러그인: 반환 타입을 보고 자동 삽입 →
// @ApiResponse({ status: 200, type: ExampleDto })
```

"실행 전"이라는 조건이 이 버그의 뿌리다 — 실행 전의 코드에서 값을 읽는 데는 한계가 있으니까.

### 2.3 AST(구문 트리) — 컴파일러가 코드를 보는 방식

컴퓨터에게 소스 코드는 처음엔 글자의 나열이다. **파싱** = 그 글자들을 문법 구조에 따라 나무 모양으로 정리하는 것(사람이 문장을 주어/동사/목적어로 분해하듯):

```
@ApiResponse({ status: 400 })              @ApiResponse({ status: HttpStatus.BAD_REQUEST })

속성 status                                 속성 status
└─ 값: 숫자 리터럴 "400"                     └─ 값: "점 접근" 구조
   (종류가 '숫자'라고 명시돼 있음)               ├─ 왼쪽 이름: HttpStatus
                                               └─ 오른쪽 이름: BAD_REQUEST
                                               (400이라는 숫자는 어디에도 없음!)
```

`HttpStatus.BAD_REQUEST = 400`이라는 사실은 다른 파일(`@nestjs/common`의 enum 정의)에 있다. **나무만 보는 코드에게 enum 참조는 "점으로 연결된 이름 두 개"일 뿐이다.**

### 2.4 enum과 "인라인" — 컴파일러는 원래 이 값을 안다

TS 컴파일러는 `.ts`→`.js` 변환 때 enum 이름을 실제 값으로 **바꿔치기(인라인)** 할 수 있다:

```ts
if (code === HttpStatus.BAD_REQUEST)   →   if (code === 400)
```

이 치환이 가능하려면 컴파일러 내부에 "이름→값" 해석 능력이 이미 있다는 뜻이고, 그 능력이 `typeChecker.getConstantValue()`라는 API로 노출되어 있다. **이번 수정의 1단이 빌려 쓴 게 바로 이것.**

## 3. 버그의 전모 — 인과 사슬

판정 함수 `isSuccessOrRedirectApiResponseArg()`의 반환값 의미:
- `true` = "이건 성공 응답 선언이다" → **자동 생성 억제**
- `false` = "에러 응답일 뿐이다" → 자동 200 계속 생성

판정은 status 값을 AST에서 읽어 `< 400` 산수로 한다. 리터럴(`400`, `'2XX'`)은 판정되지만, `HttpStatus.BAD_REQUEST`는 나무에 숫자가 없어 산수를 못 한다. 기존 코드는 이 경우:

```ts
// 수정 전: 비리터럴 → 판정 포기
return true;   // "모르겠으면 성공으로 간주"
```

인과 사슬:

```
사용자: 실패 케이스(400)를 enum으로 문서에 추가
  ↓ 플러그인: enum 값을 못 읽음
  ↓ "모르면 성공으로 치자" ← 잘못된 기본값
  ↓ "성공 응답이 이미 있네? 자동 200은 생략"
  ↓ 성공 문서 항목 증발
```

아이러니의 핵심: **실패 케이스를 성공 케이스로 오분류**한 탓에 "성공은 이미 문서화됐다"는 착각이 생겨, 사용자는 실패 항목을 *추가*했을 뿐인데 성공 항목을 *삭제*당했다. 숫자 리터럴로 쓰면 멀쩡하고, 권장 스타일인 enum으로 쓰면 깨지는 고약한 회귀였다.

## 4. 수정 — 4층 구조의 해석기

수정의 본질: **"모르겠다(포기)"를 "알아내겠다(해석)"로.** 함수 전체가 4개 층으로 재구성됐다.

### 관문 0 — 값을 "직접 적은" 경우 (기존 코드, 무변경)

```ts
if (ts.isNumericLiteral(init)) return Number(init.text) < 400;   // status: 400
if (ts.isStringLiteral(init)) return init.text === '2XX' || …;  // status: '2XX'
```

검사 대상 = **사용자가 쓴 구문의 모양.** 숫자/문자열을 그대로 적었으면 즉답.

### 바깥 관문 — "이름으로 가리킨" 모양이면 해석 구역 입장

```ts
if (
  ts.isPropertyAccessExpression(init) ||   // HttpStatus.BAD_REQUEST  (점 접근)
  ts.isElementAccessExpression(init)       // HttpStatus['BAD_REQUEST'] (대괄호 접근)
) {
```

점이든 대괄호든 표기만 다르고 뜻이 같으므로 둘 다 입장시킨다.

### 1단 — 컴파일러의 출처 추적 (모양 불문)

```ts
const constantValue = typeChecker.getConstantValue(init);
if (typeof constantValue === 'number') {
  return constantValue < 400;
}
```

`getConstantValue`의 내부 여정:

```
① "HttpStatus라는 식별자는 어느 선언에 묶여 있나?" — 스코프를 거슬러 올라감
   → import { HttpStatus } from '@nestjs/common' 발견
② import를 실제로 따라감 → node_modules의 enum 원본 선언 도달
③ 멤버 확정 — 점 접근이면 오른쪽 이름으로, 대괄호면 안이 "고정 글자"일 때만
④ 초기값(400)을 읽어 반환
```

핵심: **글자가 아니라 실체를 추적**하므로 별칭(`HS.BAD_REQUEST`), 네임스페이스(`common.HttpStatus.X`), 커스텀 enum, 대괄호-리터럴까지 전부 해석한다. 실패하는 조건도 명확하다 — ②(import 따라가기)가 안 되는 환경(예: 테스트 하네스가 존재하지 않는 파일로 program을 만들어 import가 아무 데도 도달 못 하는 경우), 또는 ③에서 괄호 안이 변수인 경우(실행 전엔 누구도 모름).

`typeof === 'number'` 가드의 검사 대상 = 사용자 구문이 아니라 **해석기의 반환값 타입.** undefined(해석 실패)와 문자열(문자열 enum)을 동시에 걸러, "모르는 걸 에러로 단정"하는 오판을 차단하고 다음 층으로 흘려보낸다.

### 2단 — 이름을 그대로 읽어서 판단 (점 접근 전용 폴백)

```ts
if (
  ts.isPropertyAccessExpression(init) &&      // ① 점 접근만
  ts.isIdentifier(init.expression) &&         // ② 왼쪽이 단순 이름 하나
  init.expression.text === 'HttpStatus'       // ③ 그 글자가 정확히 HttpStatus
) {
  const status = HttpStatus[init.name.text as keyof typeof HttpStatus];
  //             ↑ 플러그인 자신이 import해둔 "실물" enum 사전
  if (typeof status === 'number') {
    return status < 400;
  }
}
```

1단이 실패하는 환경(추적 불가)에서 대신 동작하는 대체 경로다. 추적이 불가능하니 남은 정보는 **코드에 적힌 글자뿐**이고, 글자만으로 안전하게 판단할 수 있는 모양만 처리한다:

- **왼쪽 글자 = 신원 확인**: "내가 가진 사전(`@nestjs/common`의 HttpStatus)으로 찾아도 되는 상대인가?" 글자가 `HS`(별칭)나 `common.HttpStatus`(복합)면 — 출처 추적 없이는 같은 물건인지 알 수 없으므로 — 판단을 포기한다.
- **오른쪽 글자 = 검색어**: 점 뒤에는 문법상 **반드시 고정된 이름만** 올 수 있어서 그 이름을 문자열 그대로 읽어도 100% 안전하다. 대괄호 안은 변수·계산식이 올 수 있는 자유구역이라 이렇게 문자열로 바로 읽는 방식 자체가 원리적으로 성립하지 않는다 — **이게 대괄호 접근이 2단 커버를 못 받는 이유.**
- **출구 가드 `typeof === 'number'`**: 없는 이름(오타 → undefined)과 숫자 enum의 역방향 매핑(값→이름 항목이 사전에 공존해 문자열이 나올 수 있음)을 차단.

### 3단 — 해석 불가 시 기존 동작 유지 (하위 호환 보증)

```ts
// Unknown expressions cannot be safely evaluated at compile time.
return true;
```

해석 불가 표현식은 **수정 전과 똑같이** 처리한다. 왜 `false`가 아니라 `true`인가 — 값을 모르는 채 어느 쪽으로 판정해도 누군가는 틀린다:

| 기본값 | 사실은 에러(400)였다면 | 사실은 성공(201)이었다면 |
|---|---|---|
| `true` | 200 증발 (기존과 동일) | 정확 |
| `false` | 정확 | **자동 200이 사용자의 201과 중복 — 새 회귀!** |

`true` 유지 = "이 PR로 동작이 바뀌는 유일한 집합은 1·2단이 새로 해석하게 된 것들(전부 개선)이고, 나머지는 한 글자도 안 바뀐다"는 보증. 회귀를 고치는 PR이 다른 회귀를 만들지 않게 하는 선택.

### 입력별 전체 흐름표

| 입력 | 관문0 | 1단(실빌드) | 2단(1단 실패 시) | 최종 |
|---|---|---|---|---|
| `400` | 즉답 | — | — | 정확 |
| `HttpStatus.BAD_REQUEST` | 통과 | 400 | 400 | **어디서든 정확**(이슈 케이스) |
| `HttpStatus.OK` | 통과 | 200 | 200 | 억제(올바름) |
| `HS.BAD_REQUEST`(별칭) | 통과 | 성공 | 글자 불일치로 실패 | 실빌드 정확 / 테스트선 후퇴 |
| `HttpStatus['NOT_FOUND']` | 통과 | 404 | 점 전용이라 실패 | 〃 |
| `HttpStatus[변수]` | 통과 | 멤버 미확정 | 실패 | 후퇴(무해) |
| `HttpStatus.TYPO`(오타) | 통과 | 실패 | 사전에 없음 | 후퇴 |
| `this.config.status` | 통과 | 실패 | 실패 | 후퇴 |

설계 원칙: **오판이 끼어들 틈은 가드로 전부 메우고, 판정 불가는 기존 동작으로 후퇴.** 1단은 표현식이 어떤 모양이든 실제 값을 추적해서 알아내고, 2단은 코드에 적힌 이름을 그대로 읽기만 하므로 이름이 반드시 문자 그대로 적혀 있는 모양만 처리할 수 있다.

## 6. 테스트 (최종)

두 개의 회귀 테스트가 `test/plugin/controller-class-visitor.spec.ts`에 추가됨:

1. **`HttpStatus.BAD_REQUEST`로 에러만 선언한 경우** — 자동 추론된 `200` 응답이 출력물에 그대로 남아있는지, 명시적으로 선언한 `400` 데코레이터도 그대로 유지되는지 확인.
2. **`HttpStatus.CREATED`(성공 상태)를 명시적으로 선언한 경우** — 이 경우엔 자동 추론된 `200` 응답이 나타나지 않는지 확인 (검토 과정에서 추가된 반대 방향 테스트).

4. **폴백 체인의 설계 원칙: 오판 금지, 포기 허용.** 각 단은 자신이 확실히 아는 것만 답하고(가드), 애매하면 다음 단으로, 끝까지 애매하면 기존 동작으로 후퇴한다.
5. **이 함수는 두 가지 동작(에러 상태는 응답 유지, 성공 상태는 응답 억제)을 모두 보장해야 하는데, 처음 작성된 테스트는 그중 한쪽(에러 상태 케이스)만 검증하고 있었다.** 나머지 한쪽(성공 상태를 명시하면 실제로 억제되는지)도 별도로 테스트해야, "무조건 억제 안 함"처럼 절반만 맞는 잘못된 수정도 걸러낼 수 있다.
6. **점 접근 vs 대괄호 접근의 비대칭은 문법이 만든 것이다.** 점 뒤에는 고정된 이름만 올 수 있어서 문자열로 바로 읽어도 안전하지만, 대괄호 안은 변수·계산식이 올 수 있는 자유구역이라 그렇게 읽을 수 없다. 같은 의미를 표현하는 두 문법이 정적 분석에서는 난이도가 전혀 다르다.

## 9. 개념 정리 (참고용)

- **HTTP 상태 코드**: 399 이하 성공 계열 / 400 이상 에러 계열. 요청 하나에 코드 하나.
- **Swagger 문서**: 가능한 결과들의 메뉴판. 실제 응답과 별개 — 이번 버그는 메뉴판 문제.
- **CLI 플러그인**: 컴파일 시점에 소스를 분석해 문서 데코레이터를 자동 삽입하는 도구.
- **파싱/AST**: 글자 나열 → 문법 구조 나무. 나무에는 구조만 있고 다른 파일의 값은 없다.
- **`PropertyAccessExpression`**: `A.B` 모양의 AST 노드. 오른쪽(`name`)은 문법상 항상 고정 이름.
- **`ElementAccessExpression`**: `A[...]` 모양. 괄호 안(`argumentExpression`)은 아무 표현식이나 가능.
- **`typeChecker`**: 컴파일러의 의미 분석 부서. 이름이 "어느 선언에 묶였는지"를 스코프·import를 따라 추적.
- **`getConstantValue`**: enum 멤버 참조의 상수값을 돌려주는 checker API(인라인 능력의 노출). 숫자/문자열/undefined 반환.
- **enum 인라인**: 컴파일 시 `HttpStatus.BAD_REQUEST` → `400` 치환.
- **역방향 매핑**: TS 숫자 enum 객체엔 이름→값과 값→이름이 공존(`{BAD_REQUEST: 400, 400: 'BAD_REQUEST'}`) — 사전 조회 결과에 숫자 가드가 필요한 이유.
- **`fakeProgram` 테스트 패턴**: 존재하지 않는 파일로 `program`을 만들어 트랜스포머만 검증 — import가 안 풀리므로 checker 기반 로직은 이 환경에서 폴백 경로를 탄다.
